## §A Amendments (review fixes, BE3, 2026-11-20)
- **D-B6-06 write path:** the REPEATABLE READ transaction is `READ ONLY` and only reads (counts, cursors, `now()` = `snapshot_at`). A READ COMMITTED transaction of the same job inserts the `data_export_file` rows, `export_job` + `EXPORT.CREATED`, `EXPORT.COMPLETED` and the final `running → completed`. Reason: the audit chain trigger (0003) reads the chain head with its transaction's snapshot, so a REPEATABLE READ writer failed with 23505 whenever any audit event of the tenant committed after the snapshot. D-B6-13 still holds: an erasure that failed the export leaves the final `UPDATE … WHERE state = 'running'` matching no row → `EXPORT_STOPPED`, and every file rolls back. It no longer fails with 40001. The 0602 comment on `data_export_file_guard` that says 40001 is out of date.
- **Generation job:** `int.full-export.generate` gets `expire_in = 4 hours` in the enqueue transaction. The write transaction first takes `pg_advisory_xact_lock('int.full-export:<id>')`, so a second attempt of the same job waits, then stops once the export is no longer `running`.
- **`EXPORT_TABLE_MAX_BYTES` = 128 MiB** (was 256 MiB). The cap also bounds the download, because bytea arrives as hex text: about 5x the file size in memory, and the string must stay under V8's limit.
- **BR-SEC-03:** the `export_job.filters` of a full export are `{export_id, requested_by {id, type} | null}`.
- **GET /v1/orders/export** reads at most cap + 1 rows in one statement. The audited `row_count` is the number of rows in the file. A refusal still reports the exact count.
