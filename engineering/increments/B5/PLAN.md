Standing rules for every package: tenant id only from the session (portal: also the participant id, never from input); every tenant table FORCE RLS with composite `(tenant_id, id)` FKs (database MEMORY recipe); audit every state change in the same transaction (ids only, never personal data); money and volume `bigint` minor units, over the API as decimal **strings** `^-?(0|[1-9]\d{0,17})$`, never JS `number`, never float; no shipped default thresholds, windows or deadlines (DEC-14): an unset setting means the rule is absent and the screen says so (§0 D-B5-18); refused content is never built: no income projection, earnings estimate, "potential"/"could earn" copy, next-rank prompt, recruiting target, streak, leaderboard or ranking of people, no wallet/e-pin/held-funds wording (the UI says "earnings owed to you by <tenant>"), no lead scoring, no AI recruiting content. **MONEY SAFETY:** no real money moves; PAY keeps the sandbox and bank-file adapters only (B4 D-B4-14 unchanged). **MAIL:** every mail goes through `lib/mailer sendMail(config.mailDir, …)` into MAIL_DIR; no SMS or messaging provider exists. Personal data never in logs, audit before/after, outbox payloads, job payloads, notification params or exceptions.

| D-B5-02 | **Realm design: portal accounts are `user_account.realm = 'portal'` rows linked to one participant; the database transaction stays in the tenant realm.** A portal account has `tenant_id` and `participant_id` (composite FK, CHECK `(realm = 'portal') = (participant_id IS NOT NULL)`, at most one non-deactivated portal account per participant). Its sessions have `session.realm = 'portal'`. Portal requests run in `withTenant` with the existing `app.realm = 'tenant'` and `app.tenant_id` (every tenant-isolation policy applies unchanged) **plus** `app.participant_id` (new GUC, `app_participant_id()`), actor type `user`. The session realm is derived in SQL by `app_session_realm()` = `'portal'` when `app_realm() = 'tenant'` and `app_participant_id()` is set, else `app_realm()` (used by `auth_open_session`, `auth_elevate_session`, `auth_reauth_session`). Self scope is enforced three ways: (1) `AuthContext.realm = 'portal'` with **no roles and no permissions**, and `inTenant()` refuses portal callers (403 REALM_FORBIDDEN), so every staff route refuses them; portal routes use `requirePortal()` + `inPortal()` and take the participant only from the session; (2) RESTRICTIVE RLS policies `app_participant_id() IS NULL OR <participant column> = app_participant_id()` on the personal tables (`bank_detail_request`, `bank_detail_version`, `tax_profile`, `notification`, `notification_preference`, `privacy_request`, `privacy_export`) **and the money tables** (`result_line`, `run_settlement`, `payout_instruction`, `ledger_account` by `payee_participant_id` (company accounts with NULL payee are hidden too), `posting` via its account (`EXISTS`)), `case_file` (`payload->>'participant_id' = app_participant_id()::text`: every case type a portal flow opens or reads carries `payload.participant_id`) and `case_event` via its case (`EXISTS`); on `approval` FOR INSERT `WITH CHECK (app_participant_id() IS NULL)` (a portal transaction can never approve anything); a portal transaction may insert only a `dispute` case (user-opened) or a system-opened `privacy`/`bank_detail` case (§1.3). Team view reads only `position`, `path_node` and `participant`, rank status reads `qualification_state` of owned positions only (both unaffected; their routes filter by owned positions); (3) a route-registry test (T-B5-40) calls every non-portal route with a portal session and fails on any 2xx except the allowlist of §R FR-IAM-007. Rejected: a third RLS realm `portal` (every one of ~120 tenant policies and their pinned text would change for no extra isolation: the API sets the realm either way) and tenant-realm users without a realm (staff sign-in would accept them). | FR-IAM-007 "session scoped to the participant"; SEC-26 (c) self; keeps RLS, sessions, lockout and MFA code paths. |

Every path: `auth_find_user(realm, slug, email)`, the existing attempt reservation and lockout on the account key `portal:<slug>:<email>` (separate from a staff account with the same email), `usable()` (active user, tenant not provisioning/archived) **and** the participant `active` (not merged) and not pseudonymised; every failure is the same 401 INVALID_CREDENTIALS (code failures say "The code is not valid or has expired.
